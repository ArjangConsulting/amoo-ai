# Amoo review — September 4, 2026

> Historical review of the pre-fix checkout. See [implementation status](review-implementation.md)
> for the subsequent changes and validation; source line references below describe the original state.

Amoo has a useful foundation: shared driver protocols, an explicit host/companion split, a deterministic recording/compiler/export path, app-owned test context, and command-contract tests. The highest-return work is improving the trustworthiness of execution, verification, and recovery, then making the AI surface smaller and more predictable.

This is a source review, not a device certification. I inspected the package, MCP transport and execution, session persistence, both companion server boundaries, representative driver and audit code, CI, documentation, and repository skills. Findings below distinguish observable implementation behavior from proposed improvements. I did not exercise physical devices or build the companion apps.

Validation: `make lint` passed, including SwiftFormat and SwiftLint; SwiftLint reported zero violations in 201 files. `swift test` could not run: the initial invocation could not write its module cache, and a retry using writable cache directories failed with `sandbox-exec: sandbox_apply: Operation not permitted`. Consequently, no test-pass or coverage percentage is claimed for this checkout. No implementation files were changed.

## Prioritized findings

### 1. High: an invalid session ID can operate on the default device

Evidence: [`resolveDriver`](../Sources/MCPServer/ToolExecutor.swift#L63) falls back to `defaultDriver` when a supplied session ID is missing, closed, or cannot be resolved. [`dispatch`](../Sources/MCPServer/ToolExecutor+Dispatch.swift#L11) uses that driver for mutations. Recording also skips an unresolved/inactive session.

A stale session ID followed by `device_uninstall_app`, `type_text`, or `tap` can therefore affect the default target and leave no record in the intended session. This is especially consequential when moving from one-device use to multiple simulators or real devices.

Fix: only use the default when the caller omitted `session_id`. Return typed `session_not_found` / `session_closed` errors for supplied invalid IDs. Route control-plane operations separately. Test that invalid and ended IDs invoke neither the session driver nor the default driver.

### 2. High: the Android companion listens on all network interfaces

Evidence: [`CompanionServer.kt`](../CompanionApps/Android/app/src/androidTest/java/com/amoo/companion/server/CompanionServer.kt#L48) binds `0.0.0.0`; the registered interceptor backfills descriptions, not authentication. The companion service exposes actions without a session-authentication check. The iOS companion already binds `127.0.0.1`.

The Android listener accepts connections on available interfaces; actual reachability depends on device networking/firewalls. A client that can reach it can invoke device automation. The comment explains an IPv4 forwarding issue, but wildcard binding is broader than an explicit IPv4 loopback address.

Fix: test an explicit `127.0.0.1` binding with `adb forward` on both emulator and USB hardware. Add a per-launch credential and validation interceptor for intentionally shared/remote use. Keep remote exposure an explicit configuration. Include a test that a non-loopback connection is rejected in the default configuration.

### 3. High: text verification accepts incorrect values

Evidence: [`executeSetText`](../Sources/MCPServer/ToolExecutor+Assertions.swift#L152) considers an update verified if the observed value equals the requested value **or is any changed, nonempty value**. The secure-field fallback is not restricted to secure fields.

Example: requesting `12345`, then observing truncated `123`, reports success if the field previously contained something else. Conversely, immediate single-query verification can fail when accessibility values settle later.

Fix: use bounded polling with exact equality for ordinary fields. Carry secure-entry metadata through the element contract and return an explicit verification mode for masked fields; distinguish `exact`, `masked_change`, and `unverified`. Test truncation, validation rejection, delayed updates, unchanged secure masks, and same-length secure replacements.

### 4. High: selectors silently choose the first match

Evidence: [`tap_element`](../Sources/MCPServer/ToolExecutor+Dispatch.swift#L215) and [`resolveElement`](../Sources/MCPServer/ToolExecutor+Assertions.swift#L305) use `.first`. `tap_element` then sends the observed hit point as a coordinate gesture. The row-swipe path has stronger ambiguity handling than this general tap path.

Two visible `Delete` buttons can produce a successful action against whichever element appeared first. Assertions also inherit first-match semantics instead of explicitly defining any/all/exactly-one behavior. Coordinate dispatch adds a time gap between resolving the element and hitting it.

Fix: require a unique target for mutations, returning a small candidate list on ambiguity. Support role and ancestor/container constraints. Longer term, have the companion resolve and act against a snapshot-scoped reference in one operation. Keep `target_resolved`, `gesture_dispatched`, and `postcondition_passed` distinct; the current “Tapped verified element” proves only the pre-action check.

### 5. High: session shutdown does not durably preserve the latest history

Evidence: [`SessionManager.closeAll`](../Sources/TestSession/SessionManager.swift#L201) removes sessions and closes them without flushing or draining writes. `MCPCommand` calls this during shutdown. [`persist`](../Sources/TestSession/SessionManager.swift#L103) checks its five-second interval only when another action arrives; it has no timer. `endSession` queues a save without awaiting durable completion.

After an initial flush, a few more actions followed by idle time can remain unwritten indefinitely. Closing stdin does not flush them. The advertised five-second crash window is therefore not a wall-clock bound. [`FileSessionStore.save`](../Sources/TestSession/SessionStore.swift) silently swallows persistence errors.

Fix: stop accepting mutations, close sessions, capture final reports, flush, await pending writes, then clear the registry. Use a timer or append-only journal for idle durability. Surface a recording-health state and failed-save diagnostic without failing an otherwise successful tap. Test EOF shutdown after fewer than ten pending actions, idle flushes, and an unwritable store.

### 6. High: recorded-secret handling is incomplete

Evidence: [`redactArguments`](../Sources/MCPServer/ToolExecutor.swift#L128) redacts selected text arguments, but recording stores `result.content` unchanged. [`renderViewNode`](../Sources/MCPServer/ToolExecutor.swift) includes element values; `open_url` echoes its full URL; [`SessionReport`](../Sources/TestSession/SessionReport.swift) persists launch arguments and environment verbatim.

A credential redacted during entry can subsequently appear in hierarchy output, a URL query, or launch metadata. This also produces an awkward product tradeoff: harmless text is unconditionally redacted and can block generated-test export, while other sensitive channels remain raw.

Fix: introduce explicit fixture/secret references, with field-aware artifact redaction across arguments, results, observations, URLs, and launch metadata. Persist references such as an environment-variable name instead of resolved credentials. Apply restrictive artifact permissions and configurable retention. Test the full start → type → inspect → report → plan → export path for secret leakage. Treat app labels, page text, and WebView output as untrusted data in AI guidance.

### 7. High for strict clients: screenshot output violates its advertised schema

Evidence: [`QueryTools`](../Sources/MCPServer/Tools/QueryTools.swift) declares screenshot output properties `byte_count`, `format`, and `saved_path`. [`ToolDefinition`](../Sources/MCPServer/ToolDefinition.swift) sets `additionalProperties: false`. [`executeTakeScreenshot`](../Sources/MCPServer/ToolExecutor+Assistant.swift#L179) additionally emits `original_byte_count`, geometry fields, and `scale`.

Any response containing those extra fields fails validation against the declared schema. This is a concrete contract mismatch, even if permissive clients accept it.

Fix: declare all produced fields and validate representative success/error outputs against each advertised schema. Check session tool outputs too: optional warnings/error details must be declared wherever output schemas forbid extras. Prefer schemas derived from typed result models to independently maintained dictionaries.

### 8. Medium–high: one stalled tool blocks the MCP connection

Evidence: [`MCPStdioServer.run`](../Sources/MCPServer/MCPStdioServer.swift#L93) reads blocking stdin and awaits each request before handling the next. Cancellation notifications are discarded. [`LiveCompanionRPCClient`](../Sources/CompanionProtocol/GRPCCompanionClient.swift#L452) sets explicit deadlines for swipe/scroll/drag paths, but many calls including tap, text, hierarchy, and session RPCs use defaults. Assertion loops often suppress cancellation from `Task.sleep`.

A slow build or wedged query blocks later status requests, cancellation, and calls for otherwise independent devices. Merely launching every request concurrently would introduce ordering problems on the same device.

Fix: decouple the read loop from execution, track tasks by request ID, propagate cancellation, and serialize writes. Use a per-device operation queue with concurrency between independent devices. Apply operation-specific RPC deadlines and maximum input-frame sizes. Test a hung query alongside cancellation and an independent device query; test that same-device mutations retain order.

### 9. Medium: codegen context does not survive a process restart

Evidence: [`sessionCodegenIntent`](../Sources/TestSession/SessionManager.swift#L24) exists only in memory. `SessionReport` persists the test name and launch configuration, but not context JSON/path or test description. Disk reports survive restart; the context needed to reproduce their generated tests does not.

Fix: persist versioned codegen intent with the recording. Prefer a context snapshot plus original path/hash so later edits to a context file do not silently change historical reproduction. Persist relevant compiler options as well, while preserving the documented distinction between preview-only retry tuning and final compilation. Test restart → recompile equivalence.

### 10. Medium: geometry-based recording ignores coordinate units

Evidence: [`TestSession.swipeOrigin`](../Sources/TestSession/TestSession.swift#L66) reads raw `from_x` / `from_y` from recorded arguments. The dispatcher converts pixel/normalized arguments to points for the actual gesture, but recording retains the original arguments. Target association compares those raw coordinates with point-based observed frames.

A valid swipe with `unit=pixels` or `unit=normalized` can execute correctly while binding to the wrong element, or no element, during recording.

Fix: record the resolved point coordinates and source coordinate space as execution metadata. Target inference should use resolved coordinates and snapshot identity. Test the same gesture in points, native pixels, and normalized coordinates and require equivalent target association.

### 11. Medium: AI filtering hides legitimate app controls

Evidence: [`isLikelySystemElement`](../Sources/MCPServer/ToolExecutor+AssistantFormatting.swift) removes elements using substrings including `time`, `clock`, `battery`, and `system`. Description-based element resolution uses this filtering.

An app-owned “Set timer” or “System settings” control can be removed from suggestions and some fuzzy-resolution paths. This is domain-dependent behavior, not a dependable distinction between app UI and system UI.

Fix: use owner package/bundle, window, and ancestor metadata. Scope to the target app explicitly and allow system scope when requested. Test a clock app, battery dashboard, and settings app.

### 12. Medium: audit results overstate the evidence collected

Evidence: [`executeAudit`](../Sources/MCPServer/ToolExecutor+Audit.swift) collects the current UI and attaches the supplied `app_id`, without passing that ID into scoped hierarchy/element queries. With no findings, it says “Audit passed.” [`DeepLinkValidationRule`](../Sources/AuditEngine/RulePacks.swift#L84) infers a potential deep-link-validation problem from WebView presence alone. Debug-exposure detection searches visible text.

These can be useful review prompts, but they do not establish that a build is production-safe or that deep links were exercised. An audit label can also identify a different app from the UI actually inspected.

Fix: verify target identity and scope collection. Report `evaluated`, `not_evaluated`, and `insufficient_evidence` per rule. Return structured findings and evidence, retaining “No findings in the inspected screen” as the narrow conclusion. Add manifest/plist inspection or explicit attack-scenario evidence before making stronger security claims. Tune rules against benign fixtures to measure false positives.

### 13. Medium: CI does not enforce the documented device-quality promise

Evidence: [CI](../.github/workflows/ci.yml) runs Swift lint/tests and a Linux job, but does not build either companion or provision device smoke tests. [`CommandContractE2ETests`](../Tests/IntegrationTests/CommandContractE2ETests.swift#L40) skips when the companion is absent and also converts several runtime query failures into skips. A fixture hierarchy assertion even accepts launcher/SpringBoard text.

The [coverage script](../scripts/ci/test_coverage.sh) currently gates root/core/driver-group coverage at 67/70/74 percent, whereas `Architecture.md` describes 80/85/75 percent. The driver value is a combined group, not a minimum per module. The stated one-percent regression gate is not implemented there. These are configured thresholds, not measured coverage from this review.

Fix: build companions in CI when their sources/protos change. Add required simulator/emulator fixture smoke tests, with explicit opt-in strict mode where readiness/query failures fail rather than skip. Add scheduled physical-device qualification. Report skips and per-module coverage; use a documented ratchet or changed-code gate instead of promising stronger thresholds than CI enforces.

## Performance and AI token efficiency

The existing snapshot cache, screenshot scaling, scoped queries, internal assertion polling, and reusable flows are good building blocks. Extend them at the API boundary rather than relying on agents remembering many instructions.

| Improvement | Evidence / reason | Suggested acceptance measure |
| --- | --- | --- |
| One coherent observation RPC | `describe_screen` requests context, hierarchy, and interactables sequentially; suggestions request five inputs. Separate reads can also observe different UI states. | One snapshot ID and capture time across all requested fields; measure cold/warm p50/p95 latency. |
| Remove unused screenshot capture from suggestions | `buildSuggestionReport` captures an image, but deterministic suggestion code does not inspect `request.screenshot`. | Screenshot spy sees zero captures; same suggestions for the same semantic evidence. |
| Bound query output | `find_elements` renders every match; hierarchy defaults to a full tree; full session reports return all actions. | Add limit/cursor/fields/subtree filters, explicit truncation, and complete-result counts. |
| Add a compact orientation response | `describe_screen` lists only the first seven actions but structured output contains only summary/title/count. Hidden actions are not directly paginatable. | Return a bounded structured action list with selectors and `has_more`; avoid repeating summary prose. |
| Artifact-only screenshot mode | Supplying `output` still returns an inline image. Saving evidence and showing evidence need different response choices. | `return_image=false` or resource-link mode produces no image content block. |
| Screenshot size budget | Scale is optional, leaving full native resolution as the default. | Offer a documented maximum dimension and explicit original-resolution option; measure visual-task accuracy, not just bytes. |
| Screen deltas | `screenToken` hashes summary text, not complete UI state. Same-summary value/layout changes can be missed. | Snapshot-based change token with defined included fields; optionally return added/removed/changed elements. |
| Bounded action + assertion batches | Reusable CLI flows already reduce repeated planning. MCP still requires separate calls for most steps. | Add a typed bounded sequence with stop-on-failure and optional postcondition; preserve individual recorded actions. |
| Structured recoverable errors | Most errors are strings; the model must infer whether to retry, reselect, or restart. | Stable code, retryability, target, and a small candidate/remediation payload; no secrets. |
| Smaller tool catalogs when requested | Current source declares 55 tools. All are listed regardless of task mode. | Stable `drive`, `record`, `audit`, or advanced profiles; measure schema bytes and client-visible tokens. |
| Durable journal and report index | Full-history rewrites every fixed-size batch reduce the constant factor but still produce quadratic cumulative serialization as history grows. Listing sessions loads complete historical reports. | Append actions, periodically compact, index summaries, paginate history, and evict closed in-memory sessions. |

Do not equate PNG byte reduction with a guaranteed reduction in model image tokens. Likewise, tool-list pagination alone does not reduce prompt size if the client loads every page. Benchmark the actual client/model workflow.

Extend [`PerformanceTelemetry`](../Sources/AmooCore/PerformanceTelemetry.swift) with request/trace IDs, device identity suitable for redacted logs, cache hits, snapshot age, response bytes, result counts, and output truncation. Build a fixture benchmark with orientation, form fill, list-row gesture, permission dialog, WebView, and export scenarios on both platforms. Record success rate, retries, total model calls, input/output/image tokens, wall time, and p95 operation latency. Compare changes on fixed traces and tool versions.

MCP supports structured results, output schemas, resource links, and tool annotations; use those existing mechanisms for explicit responses and read-only/destructive/idempotent hints. They describe behavior and do not replace authorization. See the official [tools specification](https://modelcontextprotocol.io/specification/2025-11-25/server/tools) and [schema reference](https://modelcontextprotocol.io/specification/2025-11-25/schema). Amoo already sorts tool discovery output; retain deterministic ordering when introducing profiles.

## Architecture improvements

1. **Keep the host/companion split.** It is appropriate for lifecycle tooling versus on-device UI automation. Avoid a large rewrite while the trust defects remain.
2. **Add a typed operation boundary.** MCP currently converts JSON values to `[String: String]`, then dispatch reparses them with local defaults. Model selector, timeout, scope, coordinate space, and environment as typed values, validating once before execution. For example, invalid appearance input currently executes light mode while echoing the invalid name. Support enum/range/conditional constraints in schemas.
3. **Make ownership and ordering explicit.** A session ID is not a device lease. Add device ownership, per-device execution sequencing, startup/closing states, and cleanup ownership before enabling concurrent MCP requests. Swift actors permit reentrancy at awaits; actor isolation alone is not a workflow lock.
4. **Separate the recording compiler from MCP.** The offline `generate plan` path consumes `SessionPlanCompiler` from MCPServer, while portable plan types live in StudioProtocol. Introduce a small domain module for plans/context/compiler, leaving CLI, MCP, and Studio as adapters. Stage this by moving types and compiler dependencies before changing behavior.
5. **Unify contracts incrementally.** Tool metadata, dispatch, command coverage, Studio tools, compilation, and emitter switches encode overlapping facts. A typed operation registry can provide schema, capabilities, recording intent, and documentation, with explicit adapters where MCP and compiled-plan semantics differ. Do not hide meaningful differences such as absence versus invisibility.
6. **Make test doubles preserve production semantics.** `ProcessRunnerCommandExecutor` bypasses the argv-only mock interface for real execution because it loses working directory/environment. Its pipeline implementation runs stages sequentially without connecting stdout/stdin. Use a complete execution request model and focused subprocess integration tests before relying on mock coverage for these behaviors.
7. **Make the live-client factory unmistakable.** `GRPCCompanionClient(connection:)` creates an in-memory fixture client; only `makeLive` opens a connection. A production-looking initializer that can succeed offline is easy to misuse. Prefer explicitly named fixture factories, ideally with fixture implementations in test support.
8. **Expand compatibility information.** Startup already checks `protocol.amoo.v1` in `DefaultSessionBootstrapper`; preserve that protection. Add companion build/version, supported feature versions, and actionable mismatch responses as the proto surface evolves.

## Documentation and skills

The main documentation problem is a mixture of implemented behavior, aspirations, and historical fixes.

- Give README an install → select device → start session/companion → inspect → act → assert → end example. Separate installed-binary use from contributor builds. Include Android alongside iOS and link a real-device route for each platform.
- Correct `docs/mcp-server.md`: its prerequisites say to start the companion separately, while the current session workflow bootstraps it. Explain both managed sessions and legacy/default-driver use.
- Replace the aspirational `Architecture.md` module tree with the actual package graph, and label planned capabilities explicitly. The current package includes TestSession, StudioProtocol, TestCodeGenerator, WebInspector, and OllamaClient. Update coverage promises to the enforced values and policy.
- Update AGENTS.md's Swift tools claim from 6.0 to the manifest's 6.2 requirement. Its blanket “tests are XCTest” statement does not describe all current files: `StudioChatServiceTests.swift` uses Swift Testing. Keep the instruction to match the surrounding test style, or document a deliberate migration policy.
- Publish a four-column supported-capability matrix: iOS simulator, physical iOS, Android emulator, physical Android. Distinguish implemented, qualified on hardware, unavailable, and experimental. Include signing, system dialogs, permissions, screenshots, recording, WebViews, and lifecycle operations.
- Document verification semantics, selector ambiguity, coordinate spaces, persistence/retention, secret handling, and what “audit passed” actually means. These are public behavioral contracts.
- Add docs examples and skill tool names to drift checks. Existing command/instruction alignment tests provide a starting point; they should not only pin prose fragments.

`skills/driving-amoo/SKILL.md` is 488 lines, 4,036 whitespace-delimited words, and 26,911 bytes. All nine repository skill bodies total 183,678 bytes. These are file-size measurements, not token counts or a claim that every client loads all skills. MCP initialization instructions occupy roughly 690 source words and repeat much of the recording guidance even for a simple inspection task.

Split the driving skill into a small default workflow and references loaded only for recording/codegen, coordinate fallback, real-device setup, WebViews, and troubleshooting. A reasonable initial target is a 100–150-line entrypoint; validate its effectiveness with task benchmarks. Move naming examples, historical retry-timing explanations, and the detailed export finalization checklist into referenced guides.

Keep the cheap-tool decision table, semantic assertions, session ID requirement, and startup/recovery path in the entrypoint. Replace blanket guidance that every passing session must produce a generated test with task-specific guidance: inspection and debugging are also valid outcomes. The instruction to resolve every target before acting duplicates `tap_element`'s own query; use prior observations or an atomic selector action where sufficient, while still recording evidence needed by codegen.

Separate developer skills from the skill installed for Amoo users. Generic Vapor and broad emulator/gRPC tutorials should be opt-in contributor references rather than routine driving context. Some skill examples still use Swift tools 6.0, so version metadata alone is not enough: verify examples against the package and current build tools when updating them.

## Suggested delivery order

1. **Trust fixes:** strict session routing, Android loopback binding, exact text verification, unique mutation targets, screenshot schema repair, durable shutdown, and coordinated artifact redaction. Add focused regression tests with each fix.
2. **Quality gate:** companion build jobs, strict simulator/emulator smoke mode, visible skip counts, and a published capability/qualification matrix. Correct contradictory onboarding docs immediately.
3. **AI efficiency:** remove unused screenshot capture, introduce bounded structured queries and artifact-only screenshots, slim the driving skill, and establish token/latency benchmarks before changing defaults.
4. **Scaling and maintainability:** coherent observations, per-device queues/cancellation, journal/index storage, typed operation registry, and compiler/domain extraction. Use recorded traces to prove equivalent behavior through these refactors.

Product expansion should follow that work: reusable fixture/reset recipes, reliable system-dialog handling, failure bundles for CI, generated-test execution qualification, and broader physical-device coverage will provide more value than adding more overlapping natural-language tools.
